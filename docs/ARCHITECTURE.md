# Архитектура репозитория

Короткая карта для человека, который впервые открывает проект. Подробности — в ссылках:
правила переноса и история версий — [re/README.md](../re/README.md), разрывы native и переключатели отладки —
[NATIVE_GAPS.md](NATIVE_GAPS.md), журнал шагов — [PLATFORM_PLAN.md](PLATFORM_PLAN.md),
указатель модулей `re/game/` — [MODULES.md](MODULES.md), что похоже на мёртвый код, но оставлено — [DEAD_CODE_AUDIT.md](DEAD_CODE_AUDIT.md).

## Идея

`Game.exe` (Driver PC, 1999, MSVC 6) переписан на C функция за функцией в стиле re3. Один и тот же код игры
(`re/game/`) собирается в две цели:

| Цель | Что это | Как собрать |
|---|---|---|
| **native** | самостоятельная программа на SDL2 + OpenGL 3.3 (Linux, macOS arm64, Windows x64); нужны только данные игры (`Data_Files`) | `cmake -S re -B build-native && cmake --build build-native` или `re/build.sh native` |
| **hook** | прокси `DINPUT.dll` (i686) для оригинального `Game.exe`: перенесённые функции ставятся поверх оригинальных (JMP rel32), так каждую можно сверить в живой игре | `re/build.sh hook` (mingw `i686-w64-mingw32-gcc`) |

CI ([.github/workflows](../.github/workflows)): Linux — native + ctest, native с SDL3 (`RE_SDL3_COMPAT`, Steam Controller), hook; macOS 14 (arm64) — native, ctest, `Driver.app`.

## Как код игры связан с двумя целями

**Глобальные переменные — `GAME_VAR` (`re/game/gvar.h`).** В hook-сборке имя раскрывается в ячейку оригинального
Game.exe по её адресу. В native — обычная C-переменная; если адрес лежит в `.rdata/.data` (00546000..0057c000),
то в режиме игры переменная живёт в образе этих секций (`data_image.c`, `re_gvar`): у одного адреса может быть
несколько имён-псевдонимов, и запись через любое видна всем. Блоки `#pragma push_macro … /*gvi*/` в файлах
расставляет `tools/gen_gvar_img.py` — руками не править.

**32-битные указатели игры — `re_ptr` / `re_addr` (`re/game/reptr.h`).** Поля-указатели в таблицах игры в native
хранятся как адреса Game.exe; перевод в родной указатель и обратно — только через реестр областей `reptr.c`.
Указатели на функции — `re_fn(адрес)`: таблица `fn_table.c` (адрес → перенесённая функция, генерируется из
`install.c`) и `thunk_table.c` (переходники `jmp rel32` Game.exe → цель).

**Ещё не перенесённые / маршрутизируемые вызовы — `re/game/unported.h`.** X-макрос-список «имя, адрес, сигнатура».
hook: вызов оригинала по адресу. native: слабая заглушка из `platform/native/stubs.c` (пишет «not ported: …»),
которую перекрывает строгое определение — перенесённая функция с тем же именем или мост в `links.c`/`game_fwd.c`.
Часть записей — уже перенесённые функции, оставленные под старым именем ради тестов-шпионов (см. правила v1.65/v1.68).

**Режим округления x87 — `re/game/fpucw.h` (v2.34).** Game.exe считает логику с управляющим словом x87 0x0c7f (округление к нулю): его ставят 005283e2 (`InitFpuCw_005283E2`, при открытии экрана) и 0052840c (`P18_ClearFlag`, в начале каждого такта), 00528455 (`NoopFn00528455`) возвращает 0x037f. Поэтому `fistp` игры (у нас `lrintf`/`lrintl`/`fround`) отбрасывает дробь. hook: эти три функции выполняют настоящие `fninit; fldcw` (inline asm только для x86), библиотечные `lrintf` учитывают режим. native: CMake подключает `fpucw.h` ко **всем файлам GAME_SRC** через `-include` (gcc и clang, в том числе Apple clang); заголовок подменяет `lrintf`/`lrint`/`lrintl`/`llrintl` макросами, которые отбрасывают дробь, пока `re_fpu_chop` = 1 (его ставит `re_fpu_load_cw` из тех же трёх функций). Арифметика и 24-битная точность x87 не эмулируются. Где нужно настоящее округление к ближайшему вне кода игры — писать `(lrint)(x)` в скобках (так в P44_InitTables). Платформенный код (`platform/`) заголовок не получает. `RE_FPU_CHOP=0` — прежнее поведение (к ближайшему), для сравнения.

**Подмена в hook-сборке.** `platform/win32/install.c` перечисляет `re_hook(адрес, функция, "имя")`; функции,
которые в оригинале `stdcall` (`ret N`), получают переходник по `stdcall_tbl.h`. Отключить одну функцию в живой
игре — `re_driver.ini`, секция `[disable]`.

## Имена

- Адрес Game.exe — главный ключ. Он есть в имени (`Call0040C20B`, `P14_Fn004E3924`, `MenuRedraw409231`) или в
  комментарии рядом с функцией; по нему функция находится в `docs/functions.csv`, Ghidra и `src/`. Эти адреса не
  удалять и не переименовывать.
- `PNN_` — функция/переменная из `portedNN.c/.h`. `CallXXXXXXXX` и `PNN_FnXXXXXX` в `unported.h` — вызовы по адресу.
- Переменные с адресом в имени (`P11_00b87e38`, `G6_01145A60`, `A_00D04B00`) — ячейки Game.exe; новые имена внутри
  уже описанных таблиц — макросы `*_VAR` над таблицей (cartab.h, nodetab.h, menugfx.h …), а не новые переменные.
- Мелкие помощники чтения полей (`rd32`, `wr32`, `rdf`, `iabs`, `fround`) — `re/game/memrw.h`; имена полей машины —
  `re/game/carfields.h`, другие общие записи (камера режиссёра, трафик, модели, MLADDER, клавиши) — свои заголовки,
  константы фиксированной точки и углов — `re/game/fixmath.h` (см. «Соглашения» ниже).

## Соглашения о коде и именах (Code conventions / naming)

Введены веткой `readability/comments`; старый код приводится к ним постепенно, по модулям.

- **Комментарии в коде — по-английски.** Существующие русские комментарии (история переноса) не удаляются;
  английский текст добавляется рядом. Заголовок файла — короткий английский обзор перед старыми заметками.
- **Заголовок функции** — блок перед ней: `Name — Game.exe <адрес>, cdecl/stdcall`, назначение, входы/выходы,
  побочные эффекты (какие глобалы/поля пишет), отступления native. Адрес Game.exe обязателен — это ключ поиска.
- **Неизвестное помечается `TODO(RE): unsure`**, а не угадывается. Слова «likely/presumably» — только для догадок
  с обоснованием рядом.
- **Локальные переменные** получают смысловые имена, когда смысл виден из кода (`fwd_speed`, `slip_front`, `dist_lead`);
  иначе остаётся имя по смещению/адресу (`f108`, `P142_B278`). Имена функций и глобалов с адресом в имени,
  записи `install.c`/`fn_table.c`/`links.c` и псевдонимы образа данных **не переименовываются**.
- **Смещения полей** — именованные константы, а не новые структуры: поля записи машины 0x148 — `re/game/carfields.h`
  (`rd32(car + CAR_SPEED)`), у каждого поля — на чём основано имя. Запись, которую читают несколько модулей, получает
  **общий заголовок** (одно определение на смещение, неясное — `TODO(RE)`):

  | Заголовок | Что внутри | Кто использует |
  |---|---|---|
  | `carfields.h` | `CAR_*` — поля записи машины 0x148 | физика, ИИ, камеры, трафик, эффекты |
  | `dircam.h` | `DCAM_*` (байтовые смещения) / `DIRCAM_W_*` (индексы int32) записи камеры режиссёра 0x8c; типы `DIRCAM_CHASE/FLYING/INCAR/STATIC/WATCHCAR` — по строкам самого Game.exe (GetCameraTypeName, CameraDump) | director.c, dirnodes.c, ported60/61/112 |
  | `trafficrec.h` | `TREC_*` — запись трафика 0x54 (TrafficRecs, 011443e0) | ported7/63/95/102/119 (старые 103/133 — пока сырые смещения с комментариями) |
  | `modelhdr.h` | `MDL_*` — заголовок модели уровня (0x38 + массивы) | ported28 (машины), ported79 (карта), ported87 (объекты) |
  | `dik.h` | `DIK_*` — скан-коды DirectInput (значения как в dinput.h; вместе с настоящим `<dinput.h>` не включать), `KEYCFG_*` — индексы P36_KeyCfg | ported36/57/59/74/110/124, plat_di.c |
  | `ladder.h`, `city.h` | `LAD_*` — коды записей MLADDER (имена по ключевым словам исходника MLADDER, комментарий — что делает интерпретатор), `LAD_OPT_*`; `CITY_*` — индекс города/уровня P15_State | ported140/141/145 |
  | `lightobj.h` | `LO_*` — запись светового объекта (фары/блики), `HIST_FRAME` | ported143/144 |
  | `fixmath.h`, `mscript_ops.h`, `memrw.h` | см. ниже | везде |

  Константы, нужные одному файлу (индексы записей ИИ копа, состояния трафика `TRF_*`, флаги меню …), — локальные
  `enum`/`#define` в своём файле. Если такая запись понадобилась второму модулю — перенести её в общий заголовок,
  а не копировать. При расхождении имён у разных модулей выбирается лучше обоснованное (строки самого Game.exe >
  ключевые слова его скриптов > поведение кода), второе толкование остаётся в `TODO(RE)`. Открытые вопросы
  собраны в `docs/RE_QUESTIONS.md`.
- **Числа:** `re/game/fixmath.h` — фиксированная точка 20.12 (`FX_ONE` = 0x1000 = 1.0, `FX_HALF`, `FX_SHIFT`) и углы
  (`ANG_FULL` = 4096 = 360°, `ANG_90`, `ANG_MASK`); макрос только там, где число действительно этот масштаб/угол.
  Коды команд скрипта миссий — `re/game/mscript_ops.h` (`MS_SETTARGET` …), **генерируется** `tools/gen_mscript_ops.py`
  из таблицы ключевых слов MScript самого Game.exe (.data 00563980).
- **32-битная арифметика оригинала сохраняется буквально** (`W(...)`, `L(...)`, `dv(v, sh)` в ported142.c и др.),
  в том числе порядок округления; «упрощения» выражений не делаются.
- **Только эквивалентные правки.** Критерий для чисто «читательских» коммитов — машинный код не меняется:
  объектные файлы native (Release) и hook (i686 `-O1`, как `build.sh hook`) совпадают побайтно до и после правки
  (при сравнении __FILE__ выравнивается через `-fmacro-prefix-map`; `diagnostics.c` отличается только `__DATE__/__TIME__`).
  Учтите: у gcc распределение регистров зависит от **порядка объявления** локальных переменных — при переименовании
  порядок объявлений не меняйте. CMake-сборка hook идёт без оптимизации (`-O0`), там допустимы только иные смещения
  слотов стека. Плюс обычный воспроизводимый прогон (ниже).

## Проверка изменений

```sh
cmake -S re -B build-native -DCMAKE_BUILD_TYPE=Release && cmake --build build-native -j
(cd build-native && ctest --output-on-failure)        # selftest + inputtest, без данных игры
re/build.sh hook                                       # DINPUT.dll собирается
```

Воспроизводимый прогон игры (нужны свои `Data_Files`, рабочий каталог — копия, игра пишет в него):
`RE_FIXED_DT=1 RE_CARDBG=10 RE_MAX_FRAMES=1700 RE_SHOT_PNG=out.png
RE_KEYS="300:LEFT,340:LEFT,380:LEFT,460:RETURN,560:RETURN,660:RETURN,700:0x28:1000,1000:0x2d:25"
xvfb-run build-native/driver --data .` — Take A Ride, Майами. Строки `[car]`, `debug.log` и снимок должны
совпадать побайтно до и после рефакторинга. Остальные переключатели `RE_*` — в NATIVE_GAPS.md и DIAGNOSTICS.md.

## RE_PROBE — проверка гипотез RE во время игры

`re/platform/native/reprobe.c/.h` — необязательный журнал для ответов на вопросы из `docs/RE_QUESTIONS.md`.
Только native: все три точки вызова (`P142_CarsStep`, `P114_MenuStep`, показ кадра в `plat_sys.c`) стоят под
`#ifndef RE_HOOK_BUILD`, без `RE_PROBE` каждая сразу возвращается (одна проверка флага). Зонд только читает
состояние игры (тема `walk` ещё ставит нажатия в очередь `RE_KEYS`), память игры не пишет, случайные числа не
тянет — прогон без `RE_PROBE` байт в байт как раньше, объектники hook-сборки игровых файлов не меняются.

| Переменная | Смысл |
|---|---|
| `RE_PROBE=1\|all` или список `car,traffic,ped,mission,menu,walk` | темы журнала |
| `RE_PROBE_LOG=путь` | файл журнала (по умолчанию `probe.log` в рабочем каталоге) |
| `RE_PROBE_EVERY=N` | период периодических дампов в шагах физики (по умолчанию 50) |
| `RE_PROBE_SHOTS=каталог` | тема menu: PNG каждой новой таблицы меню (`menu_<адрес>.png`) |
| `RE_PROBE_WALK=файл` | тема walk: состояние обходчика меню (по умолчанию `probe_walk.txt`) |

Темы: `car` — машина игрока (+0x138, зоны повреждений, +0x58/+0x68, +0x108, +0x13c..+0x141, биты управления);
`traffic` — все живые записи TrafficRecs рядом с `P59_CellLeft` и моделью машины; `ped` — пул пешеходов
A_00C56780; `mission` — смены 00c810c4 / 00c810e8 / 00c81100; `menu` — каждая новая таблица меню (адрес, пункты,
тексты экрана); `walk` — обход меню в глубину (RETURN на каждый неопробованный пункт, ESC в конце таблицы),
состояние в файле, повторные запуски продолжают с того места, где пункт вывел из меню. Строка `R <таблица>
<пункт> skip` в файле состояния исключает пункт (например, экран Detail, где обходчик застревает).

Пример: `RE_FIXED_DT=1 RE_PROBE=car,traffic RE_PROBE_LOG=probe.log RE_KEYS=… xvfb-run build-native/driver --data .`
